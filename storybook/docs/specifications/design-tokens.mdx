# Design Tokens & Theming System

This page summarizes how the project's Design Tokens work and how to use them.<br/>
Our architecture rests on a centralized source of truth (Figma) and automated generation.

## 1. Token lifecycle (workflow)

Understanding the flow of our variables is essential to keeping the Design System consistent:

* **Source of truth (Figma & JSON)**: variables are extracted from JSON files located in `src/design-tokens/`.
* **Automated generation**: a `scripts/tokens.build.mjs` script compiles this data into several target formats.
* **SCSS/CSS files (`.scss`)**: generated into `projects/ui-kit/styles/generated/`, these are the variables (e.g. `var(--...)`) you should use when styling your layout elements / components.

## 2. Token families

Tokens are split across several files in `projects/ui-kit/styles/generated/`:

- **`_tokens-semantics.scss`**: colors tied to an interface function (e.g. action, feedback, navigation).
- **`_tokens-metrics.scss`**: structural units of measure (spacing, radius, border).
- **`_tokens-typography.scss`**: text styles (families, weights, sizes).
- **`_tokens-breakpoints.scss`**: responsive breakpoint definitions.

## 3. Semantic tokens (colors)

Use these tokens to guarantee visual consistency and automatic **Dark Mode** support.

### Name structure (anatomy)

The naming follows a strict construction logic: `[family]-[level]-[property]-[state]`.
Semantic tokens are generated **with no prefix**: the family opens the name directly
(`--actions-high-surface-default`) — there's no `token-` or `semantics-` segment.

*(The `global` domain follows a deliberately shorter, three-segment anatomy —
see [Anatomy of the `global` domain](#anatomy-of-the-global-domain) below.)*

> **Casing**: the JSON is in camelCase, the generator lowercases it **with no separator**.
> `informative.defaultHigh` therefore becomes `--informative-defaulthigh-*`, not
> `--informative-default-high-*`. When in doubt, the source is
> `projects/ui-kit/styles/generated/_tokens-semantics.scss`.

> **Outside the anatomy**: the `effects` family is **flat** (`--effects-default`,
> `--effects-highlight`, `--effects-success`, `--effects-warning`, `--effects-error`) — no
> level, property, or state. These are the emission colors feeding the composite
> shadows (see §5).

### The `[level]` segment is often composite

This is the main source of confusion when hunting for a token: `[level]` isn't
always a plain `high`/`low`. It regularly **merges** the level with a second axis, and
since the casing is lost during generation (see above), the final name can be surprising.

### Anatomy of the `global` domain

The `global` domain carries the application's **structural** colors (page
backgrounds, body text, separators). It has neither a family nor a level: its naming is
`global-[axis]-[occurrence]`, in three segments.

This choice is deliberate. The words `high`/`low` in the functional families denote an
**intent hierarchy** (primary vs. secondary button); applied to neutrals they denoted a
**contrast level**. Two meanings for one word — so the axis was replaced with an
explicit emphasis vocabulary, and the `[property]` axis with the three CSS properties
it actually targets.

        <th>Role</th>

        <td>The CSS target, named after the property: <code>background-color</code>, <code>color</code>, <code>border-color</code>.</td>
    </tr>
    <tr>
        <td><strong>2. Occurrence</strong></td>
        <td>
            <em>emphasis</em>: <code>default</code>, <code>muted</code>, <code>subtle</code><br/>
            <em>role</em>: <code>brand</code>, <code>focus</code>, <code>inverse</code>, <code>disabled</code>
        </td>
        <td>Either the neutral's emphasis degree, or a specific role. Two word families, at the same level.</td>
    </tr>
    <tr>
        <td><strong>3. State</strong> <em>(optional)</em></td>
        <td><code>hover</code></td>
        <td>Suffixed to the occurrence (<code>default-hover</code>) and <strong>omitted at rest</strong> — hence the three segments in the common case.</td>
    </tr>
    </tbody>
</table>

```scss
.ui-card {
  background-color: var(--global-background-default);  // surface background
  color: var(--global-text-default);                   // main text
  border-color: var(--global-border-subtle);           // subtle border

  .ui-card-subtitle { color: var(--global-text-muted); }        // muted text
  &:focus-visible { box-shadow: 0 0 0 2px var(--global-border-focus); }
}
```

> The full inventory and resolved values (per theme, brand and mode) are in
> [Foundations / Colors](?path=/docs/foundations-colors--docs), generated from
> `tokens.manifest.json`.

## 5. Composite styles (`styles.json`)

Some Figma tokens are **composite** (several properties in one style: shadows…). They
live in `src/design-tokens/styles.json` and are generated differently: the pipeline
**composes** a ready-to-use CSS value and exposes it **twice**: as a variable and as a
utility class, for use in both SCSS and HTML.

- Output: `--shadow-{category}-{size}` (a `box-shadow` value) + `.shadow-{category}-{size}`.
- Config: `format: "composite-styles"` output in `tokens.config.json`. Adding a
  composite type means extending the `COMPOSERS` table in `scripts/tokens.build.mjs`.
- Details and preview: **Foundations → Shadows**.

## 6. Implementation examples

```scss
// ✅ GOOD USAGE
.my-component {
  background-color: var(--global-high-surface-default);
  padding: var(--units-md);
  border-radius: var(--radius-default);
}

// ❌ TO AVOID
.my-component {
  background-color: white; // Doesn't support Dark Mode
  padding: 12px;           // Hardcoded value is forbidden
}
```

## 7. Shared structural constants (`ui-config`)

In addition to the tokens (themeable, runtime), `ui-*` components share
**structural constants** in SASS (focus ring, border, control size, transition):
the *choice* of token for a given role, shared and overridable at 3 levels
(global UI → category → component).

> Full reference of the variables, default values and override mechanisms:
> **Specifications → Configuration (ui-config)**.
